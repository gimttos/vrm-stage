# VRM Stage — 제품 설계

> **"VRM을 올리면 방송 화면이 완성되는 사이트.
> OBS 브라우저 소스 URL 하나, 씬은 링크로 공유, 트래커는 쓰던 걸 그대로."**

## 1. 포지셔닝

### 경쟁자는 VSeeFace가 아니다

현재 3D 버튜버의 실제 세팅:

| 역할 | 도구 | 서로를 아는가 |
|---|---|---|
| 아바타 | VSeeFace / VNyan / Warudo | ✗ |
| 화면 합성 | OBS | ✗ |
| 알림·채팅 오버레이 | StreamElements | ✗ |
| 반응 | 채팅봇 | ✗ |
| 트리거 | Stream Deck | ✗ |

5개가 따로 돌고 서로 아무것도 모른다. 연결하려면 VTS API · VNyan 플러그인 · VMC를
엮는 배관공사가 필요하다.

**우리는 아바타·배경·오버레이·알림·반응을 하나의 씬 그래프 + 하나의 이벤트 루프에
넣는다.** 배관공사가 사라진다. 이것이 브라우저를 선택하는 이유이며, 편의가 아니라
아키텍처 우위다.

### 하지 말아야 할 프레이밍

"브라우저에서 돌아가는 VSeeFace" — 지는 포지션. 웹캠 트래킹은 iPhone ARKit이나
OpenSeeFace를 못 이긴다. 트래킹 품질로 경쟁하지 않는다.

### 선행주자

- **Kalidoface 3D / Kalidokit** — 브라우저 + VRM + MediaPipe. 개념 검증 완료,
  **유지보수 중단.** 빈 자리이지 미개척지가 아니다.
- **VSeeFace / VNyan / VMagicMirror** — 성숙, 무료, 강력. Windows 전용, 문서 빈약.
- **Warudo** — 씬 연출 강함. 유료. 온보딩 반복·립싱크 미작동 리포트 다수.

## 2. 웨지

우선순위 순. **웨지 1이 MVP, 2·3이 그 다음, 4는 아키텍처만 열어둔다.**

### 웨지 1 — OBS 브라우저 소스에 URL 하나 (MVP)

데스크톱 툴은 윈도우 캡처 + 크로마키 삽질. 캡처가 엉뚱한 창을 잡고, 알파가 안 빠지고,
창 크기가 바뀌면 레이아웃이 깨진다.

웹이면 브라우저 소스에 URL을 붙이고 끝. 알파 네이티브, 해상도 정확, 창 관리 없음.
사소해 보이지만 매일 겪는 마찰이라 체감이 크다.

### 웨지 2 — 씬이 공유 가능한 데이터

VSeeFace의 세팅은 로컬 config에 갇혀 있어 남에게 줄 수 없다.

씬 = JSON. 배경 + 조명 + 카메라 + 오버레이 배치 + 트리거를 통째로 링크로 배포.
**VTuber 씬의 CodePen.** 커뮤니티가 자산을 만들어주는 구조 — 혼자 만드는 툴이
가질 수 있는 유일한 네트워크 효과이고, 데스크톱은 구조상 못 한다.

### 웨지 3 — 반응이 일급 시민

브라우저는 이미 Twitch/YouTube 채팅, WebSocket, fetch를 말한다.

- `!hug` → 애니메이션
- 도네이션 → 카메라 컷 + 파티클 + `BRW_Surprised` 0.8
- 재생 중인 곡 → 오버레이 자동 갱신

VSeeFace에서는 플러그인 생태계를 타야 하는 일이 여기서는 함수 호출.
트리거를 씬 JSON에 선언적으로 넣어 코딩 없이 조합 가능하게 한다.

### 웨지 3.5 — 방송 룸 (구현됨)

**"인터넷 방송"의 정의를 만족시키는 조각.** 연기하는 사람의 몸이 아바타를 움직이고
링크를 연 모두가 그것을 본다. 링크를 연 사람이 각자 자기 카메라로 아바타를 조종하면
그건 방송이 아니라 공유된 장난감이다.

핵심 판단: **픽셀이 아니라 상태를 보낸다.** 리그가 실제로 읽는 ~50개 float만 보내면
프레임당 208바이트, 시청자당 6.2KB/s다. 영상 송출이라면 필요했을 인코더·TURN·SFU가
전부 사라지고, 여전히 "웹 개발"의 범위 안에 남는다.

`TrackingSource → PoseFrame → AvatarDriver` 경계가 이걸 예상하고 있었기 때문에
`RemoteSource`는 드롭인이었다 — 드라이버와 스테이지는 한 줄도 바뀌지 않았다.
아키텍처가 값을 한 번 돌려받은 지점.

**비대칭은 서버가 만든다.** Durable Object가 `hostKey`로 발행자를 판정하고 구독자가
보낸 것은 버린다. URL에 적힌 역할을 믿으면 안 된다 — 크레딧 표시에서 이미 배운 것.

**대가:** 시청자가 로컬에서 렌더하므로 VRM 파일이 시청자에게 간다. 모델을 보호해야
하는 상황이라면 이 방식은 틀렸고 영상 송출이 답이다. 그리고 정적 사이트라는 성질이
깨진다(Worker + DO + R2). 후자는 이미 Cloudflare에 배포하고 있었으므로 감당 가능한
비용으로 판단했다.

전자는 **방송 종료 시 모델 삭제**로 완화한다. 비용 때문이 아니다 — R2에서 모델 하나는
월 $0.0002 수준이고 무료 한도의 0.15%다. 이유는 노출 창을 방송 시간으로 한정하는 것:
`avatarPermission: onlyAuthor` 모델이 방송이 끝난 뒤에도 공개 URL로 남아 있을 이유가
없다. 앞서 "라이선스 강제는 연극"이라고 적었지만, 그건 *표시*를 강제할 수 없다는 뜻이고
*보관 기간*은 실제로 통제할 수 있다.

**부수 효과:** 룸이 씬과 감정도 릴레이하므로, "편집 탭 → 실제 OBS 실시간 동기화가
안 된다"는 오래된 제약이 같이 해소됐다. BroadcastChannel은 같은 브라우저를 벗어나지
못하지만 룸은 벗어난다.

### 웨지 4 — 링크 하나로 콜라보 (나중)

콜라보 상대가 링크를 열면 그 사람 웹캠이 우리 씬의 두 번째 아바타를 WebRTC로 구동.
설치 0, 계정 0, OS 무관. 웹에서만 가능하고 아무도 안 만들었다.

**MVP 아님.** WebRTC + 상태 동기화는 별개 프로젝트 규모. 아키텍처만 열어둔다.

### 신뢰 웨지 — VRM 라이선스 인식

남의 모델을 받는 사이트의 필수 요건이면서 동시에 차별점.

- 로드 시 라이선스 메타데이터를 **읽어서 표시**
- `creditNotation: required` → 크레딧을 씬에 자동 삽입
- `avatarPermission`이 허용하지 않으면 **차단**

VRM 커뮤니티는 이 부분에 민감한데 제대로 하는 툴이 드물다. "제작자 권리를 지키는
사이트"라는 평판은 배포형 서비스에서 큰 자산이다.

**단, 클라이언트 측 강제는 연극이다.** 브라우저에서 돌아가는 코드는 누구나 고칠 수
있으므로 크레딧 오버레이를 JS로 "못 끄게" 만드는 것은 불가능하다. 실제 가치는
**의무를 사용자에게 드러내는 것**에 있고, 실질적 강제는 배포 정책(업로드 시 검증,
공유 씬에 크레딧 고정 등) 층에서 결정할 문제다. 그래서 로컬/개인 사용에서는
`?credit=0`과 패널 토글로 끌 수 있게 두되, 메타데이터는 패널에 항상 남긴다.

## 3. 아키텍처

핵심 추상화: **트래킹은 특별한 시스템이 아니라 씬 그래프의 입력 노드다.**

```
TrackingSource (인터페이스)
├─ WebcamSource        MediaPipe FaceLandmarker    ← 기본값
├─ VMCSource           WebSocket ← VSeeFace/VNyan/Warudo
├─ IFacialMocapSource  WebSocket ← iPhone ARKit
└─ RemotePeerSource    WebRTC ← 콜라보 상대        ← 웨지 4
         │
         ▼
    PoseFrame          정규화 프레임
                       { arkit: Float32Array(52),
                         headMatrix: Matrix4,
                         gaze: {x, y},
                         audioLevel: number,
                         timestamp: number }
         │
         ▼
    AvatarDriver       매핑 · 스무딩 · 원시모프 주입
         │
         ▼
    VRM  ←→  Scene     배경 · 조명 · 카메라 · 오버레이 · 트리거
```

**이 경계가 주는 것:**

- `PoseFrame`으로 정규화하면 소스를 추가할 때 아바타 코드를 안 건드린다.
  소스 하나당 어댑터 하나.
- 웨지 4의 원격 상대는 그냥 또 하나의 `TrackingSource`. 재설계 불필요.
- **트래킹이 제품이 아니게 된다.** 씬 컴포지터가 제품이고 트래킹은 교체 가능한 부품.
  품질 비판을 구조적으로 막는다.

### 이주 비용 0 전략

VSeeFace 유저에게 "갈아타라"가 아니라 **"쓰던 트래킹 그대로, 화면 합성만 여기서"**.
VMC 입력을 지원하는 순간 유입 장벽이 사라진다.

### 브리지라는 단서 — 정직하게

**브라우저는 UDP 소켓을 열 수 없고 VMC는 OSC over UDP다.** 따라서 VMC 수신에는
로컬 브리지 프로세스가 반드시 필요하며, "설치 0"이라는 문구는 이 지점에서만 깨진다.

이걸 감수하는 이유:

- VMC를 **보내는** 사람은 이미 VSeeFace/VNyan/Warudo를 돌리는 중이다. 프로세스
  하나 추가는 이 집단에게 마찰이 아니다.
- 반대로 **아무것도 없는 사람**은 웹캠 경로를 쓰고, 그쪽은 진짜로 설치가 0이다.
- 즉 "설치 0"은 신규 유저용 약속이고, 브리지는 기존 툴 유저용 다리다. 두 약속이
  같은 사람을 향하지 않으므로 충돌하지 않는다.

마케팅에서 이걸 숨기면 안 된다. "웹캠은 설치 없이, VMC는 작은 브리지 하나"로
명시하는 편이 신뢰를 얻는다.

## 4. 기술 스택

| 층 | 선택 | 근거 |
|---|---|---|
| 렌더 | three.js + `@pixiv/three-vrm` (3.5.4) | VRM 0.0/1.0 동일 로더, MToon, 스프링본·표정·lookAt 내장 |
| 트래킹 기본 | MediaPipe FaceLandmarker (`outputFaceBlendshapes: true`) | ARKit 52 계수 + 얼굴 변환행렬, GPU |

| 립싱크 | Web Audio RMS/포먼트 → `aa/ih/ou/ee/oh` | 시각 기반보다 훨씬 안정적 |
| 빌드 | Vite + TypeScript | |
| 씬 | 선언적 JSON + HTML/CSS 오버레이 레이어 | 웨지 2·3의 근거 |

## 5. 매핑 설계 — 품질을 가르는 지점

### 원시 모프 타깃을 쓴다

VRoid 출력 VRM의 Face 메시에는 **VRM 프리셋 14개 외에 원시 모프 타깃이 57개**
살아 있다 (실측: `tttt.vrm`).

```
BRW (눈썹)  5 : Angry, Fun, Joy, Sorrow, Surprised
EYE        14 : Close_L/R, Joy_L/R, Spread, Iris_Hide, Highlight_Hide ...
MTH (입)   19 : Up, Down, Small, Large, Angry, SkinFung_L/R ...
HA (치아)  13 : Fung1~3, Short, Up/Low ...
ALL         6 : Neutral, Angry, Fun, Joy, Sorrow, Surprised
```

**VRM 프리셋 14개에는 눈썹이 없다.** 그래서 대부분의 툴에서 VRoid 모델은 눈썹이
안 움직인다. `BRW_*` 모프를 직접 구동하면 움직인다 — 규격 우회가 아니라 glTF
모프 타깃의 정당한 사용. 표정 표현력에서 즉시 차이가 나는 지점.

### 규칙

- **ARKit 52 → VRM 프리셋 14는 정보 손실 매핑**이다 (특히 입·볼). 눈썹은 프리셋
  대신 `BRW_*` 원시 모프 직접 주입.
- **시선은 `ParamEyeBall` 흉내내지 말고 VRM `lookAt` 사용.** VRoid 모델은 `bone`
  타입에 레인지맵까지 들어 있다 (실측: `rangeMapHorizontalInner/Outer`,
  `rangeMapVerticalDown/Up`).
- **머리 회전은 head 단독이 아니라 head/neck에 분배** (대략 6:4). 단독이면 목이
  꺾인 것처럼 보인다.
- **스무딩이 "허접함"과 "괜찮음"을 가른다.** One-Euro 필터 + 데드존.
- **깜빡임은 스무딩하지 않는다.** 뭉개면 졸린 눈이 된다. 블링크는 별도 스냅 처리.
- **좌우 반전 주의.** VRM `blinkLeft`는 *모델의* 왼쪽이고 미러링된 웹캠은 뒤집혀
  들어온다. 거의 모든 구현이 여기서 한 번 틀린다.

## 6. 로드맵

### MVP (웨지 1)

1. VRM 드래그&드롭 로드 — VRM 0.0 / 1.0 양쪽, MToon + 스프링본 구동
2. 웹캠 → 머리 회전 + 블링크 + 턱 열림. **이것만으로 이미 마법처럼 느껴진다.**
3. 투명 배경 + OBS 브라우저 소스로 바로 물리기
4. 라이선스 메타데이터 표시

### 그 다음

5. VMC / iFacialMocap 입력 (이주 비용 0 전략)
6. `BRW_*` 원시 모프 눈썹 구동 + 오디오 립싱크
7. 씬 JSON + 링크 공유 (웨지 2)
8. 트리거 시스템 + 채팅 연동 (웨지 3)

### 열어두고 안 만드는 것

9. WebRTC 멀티 유저 콜라보 (웨지 4)

## 7. 정직한 리스크

- **웹캠 단독 트래킹은 깊이가 없다.** 혀·볼 부풀리기·미묘한 입모양은 안 된다.
  기대치 관리 필요.
- **단일 웹캠 전신은 실패한다.** 얼굴 + 상체가 스윗스팟. 손은 지터가 심하다.
  (VRoid 모델에 손가락 30관절이 있긴 하다 — 나중 여지로만 둔다.)
- **프레임 예산.** MediaPipe와 VRM 렌더가 GPU를 같이 쓴다. 트래킹 30fps로 내리고
  렌더 60fps로 보간하는 것이 정석.
- **모델 로딩.** 15MB VRM. 남이 올린다면 IndexedDB 캐시 필요. 서버 저장은
  저작권·용량 문제가 바로 붙으므로 **초기에는 서버 저장 없이 로컬 파일만** 받는다.

## 8. 테스트 픽스처

| 파일 | 규격 | 용도 |
|---|---|---|
| `tttt.vrm` | VRM 1.0 (`VRMC_vrm`, `VRMC_springBone`, MToon) | 1.0 경로 회귀 |
| `reee.vrm` | VRM 0.0 (`VRM`) | 0.x 경로 회귀 |

동일 모델(VRoid Studio 2.14.0, 54 본, 17 머티리얼, 27 스프링)의 양쪽 규격 출력이라
로더 분기 테스트에 이상적이다.

**주의 — 라이선스:** 두 파일 모두 `commercialUsage`가 비상업(`personalNonProfit` /
`Disallow`)이고 `modification: prohibited`, `avatarPermission: onlyAuthor`.
저자 본인 사용에는 문제 없으나, **수익화 방송에 쓸 경우 VRoid Studio에서
`personalProfit`으로 바꿔 재출력**해야 한다.
